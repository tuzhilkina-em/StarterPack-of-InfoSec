## Какие виды DNS записи существуют и за что они отвечают?
[Ресурсные записи DNS](https://yandex.cloud/ru/docs/dns/concepts/resource-record?)  
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; В системе доменных имён Domain Name System ресурсные записи (Resource Records, RR) представляют собой типизированные структуры данных, описывающие соответствие между доменными именами и различными видами информации, необходимой для функционирования сетевых сервисов.

Структура записи:
- **Name** — имя. Домен, к которому относится запись
- **Type** — тип. Назначение записи. Тип A — IPv4‑адрес, MX — почтовый сервер и т.д.
- **Class** — класс. Тип сети. Для интернета почти всегда используется IN
- **TTL** — Time To Live. Время жизни в секундах. Определяет, сколько ответ хранится в кеше резолвера. Низкий TTL ускоряет обновление, но увеличивает нагрузку на серверы
- **RDATA** — данные записи. Полезная часть. Для A — IP, для MX — приоритет и имя почтового сервера.

Через записи администраторы управляют маршрутизацией и работой сервисов, связанных с доменом.

## Типы записей

### ***A/AAAA***
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Запись типа A (Address) является фундаментальной и служит для сопоставления доменного имени с соответствующим ему IPv4-адресом. Она позволяет клиентским устройствам находить физическое расположение сервера в сети. Аналогичную задачу для протокола нового поколения выполняет запись AAAA, которая связывает имя узла с его 128-битным IPv6-адресом.

### ***CNAME*** 
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Запись CNAME (Canonical Name) реализует механизм алиасов, позволяя одному доменному имени ссылаться на другое каноническое имя, что упрощает управление инфраструктурой и балансировку нагрузки, однако накладывает ограничения, например невозможность сосуществования с другими типами записей для того же имени.

### ***MX***
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Записи MX (Mail Exchange) определяют почтовые серверы, ответственные за прием входящей корреспонденции для данного домена. Записи MX имеют приоритет: чем ниже числовое значение приоритета, тем выше значимость конкретного сервера в очереди обработки писем. По стандарту приоритет MX-записи - беззнаковое 16-битное число от 0 до 65535, больше никаких ограничений нет. При отправке почты выбирается MX-запись с наименьшим приоритетом. Если таких записей несколько, то из них выбирается случайная. Если сервер недоступен, выбирается запись со следующим приоритетом и т.д.

#### Cтруктура записи и принцип ее работы
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Каждая запись MX содержит несколько ключевых компонентов, которые DNS-сервер использует для обработки запросов на маршрутизацию электронной почты:
- **Тип** идентифицирует запись как запись MX
- **Имя хоста** указывает домен, к которому относится запись (например, example.com)
- **Адрес почтового сервера** идентифицирует почтовый сервер, ответственный за прием электронной почты для данного домена.
- **Значение приоритета** — это число, которое определяет предпочтительный порядок, в котором следует связываться с почтовыми серверами.
- **TTL** (время жизни) определяет, как долго запись хранится в кэше DNS-серверов, прежде чем потребуется новый поиск

Технически, процесс маршрутизации электронной почты с помощью записей MX выглядит так:

1. Инициирование электронной почты: Когда пользователь отправляет электронное письмо на адрес user@example.com, его почтовый сервер должен найти, куда его доставить
2. DNS-запрос: Отправляющий почтовый сервер запрашивает DNS о записях MX, связанных с example.com.
3. Выбор приоритета: DNS возвращает все записи MX с их значениями приоритета. Сервер выбирает запись с наименьшим номером приоритета (наивысшим приоритетом).
4. Попытка подключения: Почтовый сервер пытается подключиться к основному почтовому серверу, указанному в записи MX.Обработка отказов: Если основной сервер недоступен, система автоматически пробует следующую запись MX с наивысшим приоритетом, обеспечивая непрерывность доставки электронной почты.


### ***NS***
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Запись NS (Name Server) определяет авторитетные серверы имен, которые содержат актуальную информацию о зоне и управляют всеми остальными записями в ней. Делегирование управления поддоменами также осуществляется через указание соответствующих NS-записей. Иногда NS-серверы для домена находятся на его поддоменах.
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; С точки зрения формата TXT-запись содержит одну или несколько текстовых строк, каждая из которых ограничена 255 байтами, но может объединяться в логически целое значение. Эти строки интерпретируются не самим DNS, а прикладными протоколами, которые определяют собственную семантику содержимого.


### ***ТXT*** 
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; TXT-записи в DNS представляют собой универсальный механизм хранения произвольных текстовых данных, ассоциированных с доменным именем. Изначально они задумывались как средство для размещения человекочитаемой информации, однако в современной практике их основное назначение — передача машиночитаемых политик и метаданных, используемых различными сетевыми сервисами. Как пример - механизм SPF (Sender Policy Framework) использует TXT-записи для указания перечня серверов, имеющих право отправлять почту от имени домена. DKIM (DomainKeys Identified Mail) публикует в TXT-записях открытые ключи, с помощью которых принимающая сторона проверяет цифровую подпись письма. DMARC объединяет эти механизмы и задаёт политику обработки сообщений, не прошедших проверку. 
  
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Кроме почтовых систем, TXT-записи применяются для подтверждения владения доменом. Различные сервисы (облачные платформы, системы доставки контента, удостоверяющие центры) требуют разместить уникальную строку в TXT-записи, чтобы убедиться, что заявитель контролирует домен. Это используется, например, при выпуске TLS-сертификатов через DNS-based валидацию.  

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; TXT-записи также используются для хранения произвольных настроек приложений, включая параметры SIP, политики безопасности, ключи API и другие служебные данные. Благодаря своей гибкости они стали фактически стандартным способом расширения DNS без введения новых типов записей.

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; С точки зрения безопасности TXT-записи не имеют встроенных механизмов защиты от подмены, поскольку базовый DNS не предусматривает аутентификации. Для обеспечения целостности и подлинности используется расширение DNSSEC, которое добавляет цифровые подписи к записям. Без этого TXT-записи уязвимы к атакам, связанным с подменой ответов DNS.



### ***SOA*** 
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; SOA-запись (Start of Authority) в DNS определяет её административные и операционные параметры. Каждая зона обязана содержать ровно одну SOA-запись, которая служит точкой отсчёта для всех процессов, связанных с обслуживанием и репликацией зоны.

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Семантически SOA фиксирует, какой сервер является первичным источником данных зоны и кто отвечает за её администрирование. Она содержит несколько строго определённых полей. Первое — это имя главного (primary) авторитетного сервера, на котором хранится исходная версия зоны. Второе — адрес администратора зоны, записанный в виде доменного имени (с заменой символа «@» на точку). 

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; У этой записи также есть технический параметр - серийный номер (serial). Он используется вторичными (secondary) DNS-серверами для определения необходимости обновления зоны. При каждом изменении зоны серийный номер должен увеличиваться; вторичные серверы периодически сравнивают своё значение с первичным и при обнаружении расхождения инициируют зоновый трансфер. От корректного управления этим полем напрямую зависит согласованность данных в распределённой системе DNS.

Остальные параметры SOA управляют поведением репликации.  
- Refresh (Обновление): Период времени (в секундах), через который вторичный сервер должен запрашивать SOA-запись у основного для проверки изменений.
- Retry (Повтор): Время ожидания перед повторной попыткой обновления, если первичный сервер недоступен.
- Expire (Истечение): Время, в течение которого вторичный сервер считает свои данные актуальными, если первичный сервер не отвечает.
- Minimum TTL (negative caching TTL): Время кэширования для отрицательных ответов (если записи не существует).




### ***SRV***
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Запись SRV (Service Locator) представляет собой специализированный тип ресурсной записи DNS, предназначенный для идентификации серверов, предоставляющих конкретные сетевые службы. В отличие от стандартных записей типа A, которые лишь сопоставляют имя с IP-адресом, запись SRV реализует механизм обнаружения сервисов, указывая протокол, порт и параметры приоритетности. В архитектуре AD  именно через записи SRV клиентские рабочие станции находят контроллеры домена для выполнения процедур аутентификации, применения групповых политик и доступа к глобальному каталогу.  

Запись SRV имеет строго регламентированный формат:
- Служба (_service): Символическое имя службы, всегда начинающееся с нижнего подчеркивания (например, _ldap, _kerberos, _gc). Это исключает путаницу с именами обычных хостов.  
- Протокол (_proto): Указывает на транспортный уровень передачи данных, обычно _tcp или _udp
- Имя (name): Доменное имя, к которому относится данная служба
- Приоритет (Priority): Целое число, определяющее иерархию использования серверов. Клиент всегда обращается к узлу с наименьшим значением приоритета. Если этот сервер недоступен, выбирается следующий по возрастанию приоритета
- Вес (Weight): Механизм балансировки нагрузки для записей с одинаковым приоритетом. Сервер с большим весом будет получать пропорционально больше запросов от клиентов
- Порт (Port): Номер порта, на котором служба ожидает соединения (например, 389 для LDAP или 88 для Kerberos). Это позволяет запускать службы на нестандартных портах без изменения конфигурации каждого клиента
- Целевой узел (Target): Каноническое доменное имя (FQDN) хоста, предоставляющего услугу. Оно должно разрешаться в конечный IP-адрес через запись типа A  

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Процесс обнаружения контроллера домена (DC Locator) полностью опирается на SRV-записи. Когда компьютер вводится в домен или пользователь инициирует вход в систему, операционная система отправляет запрос к DNS-серверу для поиска записи вида _ldap._tcp.dc._msdcs.DnsDomainName.
Если данные записи отсутствуют или повреждены, клиент не сможет определить, какой сервер в сети является контроллером домена, что приведет к ошибке, даже если серверы физически доступны и отвечают на ping. Служба Netlogon на контроллере домена несет ответственность за автоматическую регистрацию и периодическое обновление этих записей в зоне DNS.  


### ***PTR***
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Запись PTR (Pointer), или указатель, представляет собой специализированный тип ресурсной записи DNS, предназначенный для выполнения операции обратного преобразования (Reverse Lookup). В то время как стандартные записи типа A связывают доменное имя с IP-адресом, запись PTR выполняет противоположную функцию: она позволяет по известному IP-адресу определить каноническое имя хоста (FQDN).
Функционирование записей PTR неразрывно связано с существованием специальных зон обратного просмотра в пространстве доменных имен, имеющих иерархию в домене in-addr.arpa для протокола IPv4 и ip6.arpa для IPv6.
>in-addr.arpa — это специальный домен верхнего уровня, используемый в системе DNS для «обратного поиска» (reverse DNS lookup) —
>определения доменного имени по его IPv4-адресу.  
>Он позволяет сопоставить IP-адрес (например, 8.8.8.8) с именем хоста (dns.google), используя записи типа PTR (pointer)

#### Структура и механизм именования
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Запись PTR требует специфического формата записи IP-адреса, который записывается в обратном порядке. Это необходимо для соблюдения логики иерархии DNS, где наиболее общие элементы (домены верхнего уровня) находятся справа, а частные (узлы) — слева. Октеты IP-адреса инвертируются, чтобы соответствовать древовидной структуре DNS. Также в записи указано полное доменное имя (FQDN) сервера, которому принадлежит данный адрес.

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Наличие корректных записей PTR является обязательным условием для стабильной работы ряда сетевых сервисов и протоколов безопасности:
- Верификация почтовых серверов: Большинство современных почтовых систем проверяют наличие PTR-записи у отправляющего сервера. Если IP-адрес отправителя не разрешается в доменное имя или имя не совпадает с заявленным в заголовках письма, сообщение с высокой вероятностью будет заблокировано как спам.
- Диагностика сети: Утилиты трассировки и мониторинга (например, tracert или nslookup) используют PTR-записи для отображения понятных имен узлов вместо цифровых адресов, что существенно упрощает анализ топологии сети
- Безопасность и аутентификация: Некоторые протоколы, такие как Kerberos или SSH, могут выполнять проверку обратного просмотра для подтверждения подлинности узла и предотвращения атак типа "человек посередине" (MITM)
- Логирование: Системы сбора логов часто преобразуют IP-адреса подключающихся клиентов в имена хостов для повышения читаемости отчетов и облегчения последующего аудита

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; В AD записи PTR могут создаваться автоматически при регистрации клиентским компьютером своей записи типа A, если на DNS-сервере предварительно настроена соответствующая зона обратного просмотра. Отсутствие таких зон и записей не блокирует работу домена напрямую (в отличие от записей SRV), однако значительно затрудняет поиск неисправностей и может приводить к задержкам при установке сессий по протоколам, требующим обратной проверки

### Просмотр DNS-записей

#### nslookup
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Действует на ОС Windows и Linux. С помощью этой утилиты можно точно узнать информацию об IP-адресе, а еще о настройке всех ресурсных записей. Утилита запускается через cmd в Windows и nерминал в Linux. Для обоих случаев она будет выглядетьпримерно так:  
> nslookup -type=тип_записи site.com


#### Утилита dig (Domain Information Groper) 
спользуется в системах Unix и Linux для запросов к DNS-серверам. Она предназначена для получения информации о DNS-записях и диагностики проблем связанных с DNS. Dig позволяет пользователям выполнять запросы к определенным DNS-серверам, получать подробную информацию о различных типах DNS-записей, включая A-записи (адреса), MX-записи (почтовые серверы), NS-записи (серверы имен) и другие.

~ % dig что-то.ru - А записи  
~ % dig -x 193.232.59.17 - ptr записи  
~ % dig что-то.ru SOA - soa записи  
~ % dig что-то.ru MX - мх записи  
~ % dig _dmarc.что-то.ru TXT - тхт записи и т.д.

###### После получения результатов можно воспользоваться утилитами whois и curl, утилитой openssl для проверки срока действия или цепочки доверия сертификата, а также утилитой nmap для проверки портов
