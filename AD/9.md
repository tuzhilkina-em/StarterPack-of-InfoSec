## Группы BUILTIN

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; ***Группы BUILTIN*** - это встроенные локальные группы безопасности в Windows, которые создаются системой автоматически и используются для управления правами на уровне конкретного компьютера. Они хранятся в локальной базе (SAM) и имеют префикс BUILTIN\, например: BUILTIN\Administrators, BUILTIN\Users, BUILTIN\Remote Desktop Users. У каждой группы свой SID, на который ориентируется вся система, тк имя группы изменить можно, а SID нет  

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; ***SID (Security Identifier)*** - это уникальный идентификатор безопасности, который Windows присваивает каждому объекту, связанному с доступом: пользователю, группе, компьютеру или службе. В системе SID используется для принятия решений о доступе. Формально SID, это строка, состоящая из нескольких частей: S-1-5-21-...-RID. В начале идёт версия и идентификатор издателя, а затем уникальная часть (обычно связанная с доменом или локальной системой), и в конце - RID (Relative Identifier), который определяет конкретного пользователя или группу внутри этой области  

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Windows не раздаёт права напрямую пользователям, а делает это через группы. Например, группе BUILTIN\Administrators выданы максимальные права в системе, а уже пользователи добавляются в эту группу и наследуют эти права. То же самое с группами Users, Remote Desktop Users и другими - каждая из них соответствует определённому набору разрешений. При этом в такие группы могут входить не только локальные пользователи, но и доменные. Например, можно добавить DOMAIN\user в BUILTIN\Administrators, и этот пользователь получит административные права на конкретной машине

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; При входе пользователя формируется **access token**, в который входят SID самого пользователя и SID всех групп, в которых он состоит. Когда пользователь пытается получить доступ к ресурсу, система сравнивает SID из токена с SID, указанными в ACL. На основе этого принимается решение о выдаче доступа   

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; ***ACL (Access Control List)*** - это механизм в Windows, который определяет, кто и какие действия может выполнять с объектом (папка, файл). Каждый объект в системе имеет свой список ACL, внутри которого находятся записи (**ACE - Access Control Entry**). В каждой такой записи указано:  
- какой субъект (SID пользователя или группы)
- какое действие разрешено или запрещено (чтение, запись, выполнение и тд)

В ACL есть порядок и приоритет:  
- явные запреты (deny) обычно имеют более высокий приоритет
- затем учитываются разрешения (allow)
- наследуемые правила могут применяться от родительских объектов (например, от папки к файлам)  

###### Менять ACL может только тот, у кого есть соответствующие права — обычно это владелец объекта или администратор

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Изменение ACL осуществялется с помощью утилиты **icacls**, далее указывается обычно имя объекта. Ключом /remove user можно удалить, а с помощью /grant user:F - выдать все права. Сами группы же посмотреть можно через сmd - **net localgroup**, а если после добавить имя то можно увидеть состав группы. Через Powershell это делается с помощью **Get-LocalGroup**, или **Get-LocalGroupMember -Group "Administrators"** для списка участников

## Еще о группах
В AD для используется класс объекта group, а тип и область действия технически задаются через атрибут groupType  

### Security&distribution
- *Security group* - группа безопасности. Она используется для выдачи прав доступа. Такую группу можно добавить в ACL файла, папки, сетевого ресурса, объекта AD, GPO-фильтра, локальной политики. При входе пользователя в систему SID его security-групп попадает в access token, и дальше Windows сравнивает SID из токена с SID в ACL  
- *Distribution group* - группа рассылки. Она используется для почты и не участвует в авторизации. Её нельзя использовать как субъект безопасности для выдачи NTFS-прав или прав на объекты AD  


### Встроенные группы AD
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Встроенные группы создаются автоматически при создании домена. Они нужны для стандартных административных задач и системных механизмов  

- *Domain Admins* - RID обычно заканчивается на -512. Участники этой группы имеют административный контроль над доменом и, как правило, являются локальными администраторами на доменных компьютерах через стандартные политики и членство в Administrators на DC
- *Enterprise Admins* - группа уровня леса. Она находится в корневом домене леса и по умолчанию входит в встроенную группу Administrators во всех доменах леса
- *Schema Admins* - группа, которая может изменять схему AD. Изменение схемы влияет на весь лес, потому что схема определяет, какие классы объектов и атрибуты вообще существуют в каталоге
- *Account Operators* - группа для управления пользователями и группами без полного Domain Admin. Она может создавать, изменять и удалять многие учётные записи и группы, но не должна управлять самыми защищёнными административными группами
- *Remote Desktop Users* - группа, участники которой могут входить по RDP, если это разрешено политиками и локальными настройками
- *dns&dhcp Admins* - админы днс и dhcp серверов
- *Domain Users* - стандартная группа всех обычных пользователей домена, RID обычно -513
- *Domain Computers* - группа для компьютеров домена. Используется для назначения политик или прав компьютерам как объектам безопасности
- *Domain Controllers* - группа контроллеров домена, в неё входят DC конкретного домена
- *Enterprise Domain Controllers* - группа контроллеров домена на уровне леса. Используется для междоменных и лесовых механизмов
- *Protected Users* - глобальная группа безопасности Active Directory, предназначенная для защиты от атак кражи учетных данных. Группа активирует неконфигурируемую защиту на устройствах и хост-компьютерах, чтобы предотвратить кэширование учетных данных при входе участников группы. Когда пользователь входит в группу Protected Users, группа обеспечивает следующее:
  - Делегирование учетных данных (CredSSP) не кэширует учетные данные в формате обычного текста, даже если пользователь включает параметр групповой политики Разрешить делегирование учетных данных по умолчанию  
  - Дайджест Windows не кэширует учетные данные обычного текста пользователя, даже если они включили Дайджест Windows  
  - NTLM прекращает кэширование открытых учетных данных пользователя или использование односторонней функции NT (NTOWF)  
  - Kerberos останавливает создание ключей шифрования данных (DES) или RC4. Kerberos также не кэширует учетные данные обычного текста пользователя или долгосрочные ключи после получения первоначального билета предоставления билета (TGT)  
 После добавления новой учетной записи пользователя в группу защищенных пользователей эти защиты активируются при входе нового защищенного пользователя на свое устройство
