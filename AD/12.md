## Как хост находит контроллер домена?
### Процесс поиска DC по DNS
 Алгоритм поиска контроллера домена (DC locator) состоит из двух частей и строистя в основном на dns:  
- Указатель находит, какие контроллеры домена зарегистрированы  
- Указатель отправляет запрос на поиск контроллера домена в указанном домене  

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Механизм поиска контроллера домена в Active Directory формализован как алгоритм DC Locator и реализуется службой Netlogon на клиенте, решая вопрос необходимости идти в сеть или можно использовать кэш. Внутри процесс начинается с вызова функции DsGetDcName - API, которое обращается к Netlogon. Кэш хранит последний успешный контроллер и параметры его пригодности. Если контроллер недавно использовался и не было ошибок, клиент попытается использовать его повторно, что снизит нагрузку на DNS и сеть  

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Если поиск по кэшу не прошел, далее происходит этап dns-обнаружения. Контроллеры домена при старте регистрируют [SRV-записи](https://github.com/tuzhilkina-em/StarterPack-of-InfoSec/blob/6f81efd0e137c031ba5b6380b8cfafb956e11e1f/DNS/1.md) в зоне DNS. Есть нюанс: клиент не подключается к первому dc из списка. Это происходит с целью гарантии работы контроллера тк он может быть недоступен или загружен. Для проверки работоспособности клиент отправляет CLDAP-запрос по UDP 389 (ldap но по udp, без установления соединения). Ответ содержит инфу о службе каталогов. Если DNS отвечает, но контроллеры недоступны на уровне сети, клиент будет перебирать список, отправляя LDAP ping каждому кандидату    

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Если Netlogon не работает на клиенте, алгоритм вообще не запускается, так как именно он реализует DC Locator. Если не работает на контроллере, тот не регистрирует себя в DNS и становится «невидимым» для клиентов, несмотря на то что сам AD может функционировать.

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Если LDAP ping проходит, но дальше ломается Kerberos, клиент всё равно увидит контроллер, но не сможет аутентифицироваться. Внутренне вся система работает за счёт распределённости. Нет центрального списка контроллеров. Каждый DC сам регистрирует себя в DNS и участвует в репликации. Клиенты выполняют поиск каждый раз заново (или из кэша), что делает систему устойчивой к отказам отдельных узлов

### Поиск по NetBIOS
###### Начиная с ws25 использовать имена NetBIOS не выйдет тк обратной совместимости нет
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Обнаружение на основе NetBIOS включает в себя регистрацию записей контроллеров домена в службе интернет-имен Windows (WINS). Клиенты запрашивают WINS для соответствующих записей, за которым следует связь с возможными целевыми целевыми контроллерами домена. В этом режиме используется широковещательный механизм, поддерживаемый сообщениями [mailslot](https://learn.microsoft.com/ru-ru/windows/win32/ipc/about-mailslots), в которых клиент передает пакеты в локальной сети для поиска ЦОД

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Когда приложение запрашивает контроллер домена, но указывает короткое доменное имя в стиле NetBIOS, производится сопоставление имени NetBIOS с DNS-именем домена. Если сопоставление успешно, далее используется обнаружение на основе DNS, при чем сопоставление производится с учетом приоритезации:  
1. Кэшированные сведения из предыдущей подстановки  
2. Все домены в текущем лесу  
3. Имена верхнего уровня (TLN) для всех доверенных лесов и внешних доверий  
   
Для Windows Server 2025 и более поздних версий:  
1. Сопоставления доменных имен, настроенных администратором  
2. Сопоставления доменных имен для всех лесов и дочерних доменов в доверии к лесу  
3. Сеансы входа на клиентском компьютере







###### Начиная с Windows Server 2025, Netlogon загружает и кэширует сведения об именовании доменов и дочерних доменов во всех доверенных лесах. Эта информация используется при сопоставлении доменных имен в стиле NetBIOS с DNS-доменными именами
