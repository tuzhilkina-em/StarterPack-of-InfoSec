## Процесс построения топологии репликации КСС

### Про процесс репликации

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Репликация Active Directory - это механизм синхронизации данных каталога между контроллерами домена, задача которого состоит в том, чтобы все DC в домене или лесу имели согласованное состояние базы AD. Когда пользователь меняет пароль, создается группа, обновляется GPO или изменяется любой атрибут объекта - изменение сначала записывается только на одном контроллере домена. После этого изменение должно распространиться на остальные DC через репликацию. Active Directory использует multimaster replication. Это означает, что почти любой контроллер домена может принимать изменения. Нет одного DC, который хранит единственную копию каталога, каждый writable DC содержит собственную копию базы AD и способен изменять объекты  
<br>  


&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Когда объект изменяется, изменение сначала проходит через LSASS и Directory System Agent, после чего записывается в ESE-базу данных. Active Directory не копирует весь объект целиком при каждом изменении, а репликация работает на уровне атрибутов. Если у пользователя изменился только один атрибут, реплицируется именно изменение этого атрибута. Каждое изменение получает replication metadata. У атрибута увеличивается version number, фиксируется originating timestamp, GUID контроллера домена-источника и новый USN. USN - это локальный счетчик изменений конкретного DC, на каждом контроллере домена он свой   
<br>  


&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Внутри сайта репликация работает через change notification. Предполагается, что внутри одного сайта сеть быстрая и стабильная, поэтому DC практически сразу уведомляют соседей об изменениях. Обычно notification отправляется примерно через 15 секунд после update. Партнер получает уведомление и запускает pull replication  
<br>  


&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; При репликации между сайтами Active Directory предполагает наличие WAN-каналов, высокой задержки и ограниченной пропускной способности. Поэтому межсайтовая репликация идет по расписанию и использует compression. По умолчанию изменения между сайтами реплицируются раз в 180 минут, хотя этот параметр является настраиваемым. Для механизма репликации используются high-watermark vector и up-to-dateness vector. Каждый DC хранит информацию о том, до какого USN каждого партнера он уже получил изменения. Когда начинается replication cycle, DC обращается к партнеру с запросом на отправку всех updates после определенного USN  
<br>  

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Up-to-dateness vector нужен для предотвращения replication loops. В топологии репликации изменения могут проходить через несколько DC и теоретически возвращаться обратно к источнику. Чтобы изменения не циркулировали бесконечно, каждый update содержит metadata источника, что исключает повторное принятие изменений. Active Directory использует eventual consistency. После изменения некоторое время существует рассинхронизация. Например, пользователь может уже существовать на DC1, но еще отсутствовать на DC2. Через некоторое время topology replication converges, и все DC получают одинаковое состояние каталога
<br>  

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Если два контроллера домена одновременно изменяют один и тот же атрибут объекта, возникает replication conflict. В большинстве случаев Active Directory использует модель Last Writer Wins. Система сравнивает version number, timestamp и originating GUID, после чего определяет, какая версия считается актуальной. Репликация идет отдельно для разных партиций каталога. Domain Naming Context реплицируется только внутри домена. Schema и Configuration partition реплицируются на весь лес. DNS application partitions могут реплицироваться только DNS-серверам, что уменьшает объем replication traffic 


С точки зрения сетевки процесс репликации использует следующие порты и протоколы:  
- 53 - dns (очев)
- 88 - kerberos (все как в ад), ну или NTLM - TCP 445 / RPC
- 135 - rpc, а уже после выдается Dynamic RPC - 49152-65535
- 3269/3269 - Global Catalog
- 445 - SMB, 5722 - DFSR - для sysvol и gpo соответственно
<br>  


## KCC в репликации
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; ***KCC (Knowledge Consistency Checker)*** - средство проверки согласованности знаний. Это встроенный процесс в Active Directory, который автоматически генерирует и поддерживает оптимальную топологию репликации между контроллерами домена. Работает он локально на каждом контроллере домена внутри LSASS как часть Directory System Agent. Примерно каждые 15 минут он анализирует состояние инфраструктуры и пересчитывает topology replication  
<br>  

Когда KCC запускается, он сначала читает данные из Configuration partition. Там хранятся:
- сайты
- site links
- transport
- NTDS Settings
- connection objects
- bridgehead servers

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; После этого KCC строит логический граф репликации. Каждый DC рассматривается как вершина графа, а replication connections - как связи между ними. В этом процессе необходимо выполнение следующих условий: достижимость DC друг для друга, оптимальное количество изменений (в целом регулируется частотой репликации). Внутри сайта предполпгается низкая задержка и стабильная сеть. Из-за этого intra-site topology строится плотнее, а базовая модель - ring topology. Каждый DC обычно получает минимум двух replication partners, что позволяет сохранить репликацию даже при отказе одного контроллера домена. KCC обычно не является простым ring-topology, анализируется количество hops между DC. Если этот параметр превосходит 3-4 hops, то ксс  создает shortcut connections (если визуализировать ring-topology как дефолтное кольцо, то shortcut connections будут его хордами)
<br>  


&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Межсайтовую topology строит **ISTG - Inter-Site Topology Generator**. Внутри каждого site выбирается один DC, отвечающий за inter-site connection objects. Это нужно, для того, чтобы несколько DC одновременно не создавали хаотичные topology changes. KCC также выбирает bridgehead servers. Это контроллеры домена, через которые сайт реплицируется с другими сайтами. Вместо того чтобы каждый DC напрямую общался через WAN с каждым DC другого сайта, inter-site replication проходит через bridgehead servers, а затем изменения распространяются внутри сайта через обычную intra-site replication
<br>  

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; KCC работает отдельно для разных naming contexts. Репликация Schema partition, Configuration partition, Domain partition и DNS application partitions может строиться независимо. Это связано с тем, что разные разделы каталога могут реплицироваться на разные DC. KCC полностью зависит от DNS. Контроллеры домена ищут партнеров через SRV-записи и GUID-based CNAME. Если DNS сломан, KCC не может корректно построить topology, из-за чего возникают replication failures и replication islands
<br>
