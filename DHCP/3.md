## Что такое DHCP guarding? 

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; ***DHCP guarding*** - технология, которая позволяет предоставлять доступ к сети только авторизованным клиентам. Она защищает клиентов в локальной сети, препятствуя получению IP-адреса от неавторизованного DHCP-сервера. Также она регулирует порядок обмена сообщениями протокола DHCP 

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; В основе защиты лежат правила, указывающие, какие порты коммутатора будут доверенными (екгыеув), а какие нет. Сообщения, приходящие через ненадёжные порты, автоматически отбрасываются коммутатором. Также для них выполняются отдельные проверки сообщений и формируется база данных привязки DHCP. Через доверенные порты коммутатора входящие DHCP-сообщения не отбрасываются и обрабатываются классическим образом

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Работа механизма основана на анализе типов DHCP-сообщений. Запросы от клиентов (такие как Discover и Request) считаются допустимыми и проходят через все порты, в то время как ответы сервера (Offer, ACK) разрешаются только с доверенных портов. Если подобное сообщение поступает с недоверенного порта, оно блокируется на уровне коммутатора и не достигает клиента. 

**То есть технически это выглядит примерно так:**  
&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Когда пакет приходит на порт коммутатора, нужно определить, что это DHCP-трафик (по UDP портам 67/68 и структуре BOOTP/DHCP, структура BOOTP - это формат сетевого пакета для начальной конфигурации клиента, который позже был расширен DHCP). Далее происходит классификация сообщения - это клиентский пакет (Discover/Request) или серверный (Offer/ACK). Это делается по полю DHCP Message Type внутри пакета. После этого применяется логика доверия порта. Если пакет пришёл с untrusted порта, коммутатор проверяет тип сообщения:
- если это клиентский запрос - он пропускается дальше по сети
- если это серверный ответ - пакет отбрасывается  

Если же пакет пришёл с trusted порта, он считается легитимным и проходит без ограничений. Параллельно с этим коммутатор извлекает данные из DHCP-пакетов и формирует таблицу привязок. В неё записываются:
- MAC-адрес клиента
- выданный IP-адрес
- номер порта, через который подключён клиент
- иногда VLAN и время аренды

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Эта таблица строится на основе сообщений DHCP ACK, когда адрес уже окончательно выдан. В дальнейшем она используется для проверки других типов трафика: например, чтобы убедиться, что устройство с конкретного порта действительно имеет право использовать данный IP.

Также коммутатор может выполнять дополнительные проверки самого DHCP-пакета. Например:
- проверять поле giaddr (чтобы избежать подмены relay)
- контролировать корректность структуры сообщения
- ограничивать количество DHCP-запросов с одного порта (защита от starvation)

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp; Таблица привязок DHCP доступна только на коммутаторе, с хоста её получить нельзя. Сам механизм защищает только DHCP-процесс, поэтому его можно обойти, например, используя статическую настройку IP или эксплуатируя отсутствие дополнительных защит, таких как IP Source Guard и DAI. Если есть доступ к самому сетевому устройству то можно сделать вот так: **show ip dhcp snooping binding**

Вообще, DHCP guarding следует рассматривать не как самостоятельный механизм защиты, а как часть комплексной модели безопасности на уровне L2. Он обеспечивает корректность процесса получения IP-адреса, но не контролирует дальнейшее поведение хоста в сети. Поэтому на практике его используют совместно с другими механизмами. Например, Dynamic ARP Inspection проверяет соответствие ARP-пакетов данным из таблицы привязок DHCP и предотвращает ARP spoofing, а IP Source Guard ограничивает возможность отправки трафика с подменённым IP-адресом, разрешая его только для известных связок IP-MAC-порт из таблицы
